## 3. Phase 4 Goals

Implement a production-oriented Skill Factory that supports this lifecycle:

`Requirement → Capability Gap → Skill Discovery → Reuse/Adapt/Create Decision → Skill Draft → Static Security Validation → Isolated Testing → Validation Report → Required Approval → Versioned Promotion → Registry Synchronization → Runtime Discovery → Rollback When Necessary`

The lifecycle must enforce these principles:

- Reuse an appropriate existing skill before considering adaptation or creating a new skill.
- Adapt an existing skill when its reusable implementation is close to the requirement and the modification is justified.
- Create a new skill only when the existing capability catalog and skill library do not provide a suitable solution.
- Never bypass required security validation, testing, or approval.
- Keep drafts, quarantined skills, and rejected candidates out of the active production skill registry.
- Publish only a validated, approved, versioned skill.
- Make published skills discoverable by the Capability Finder and the rest of the system.
- Preserve enough evidence and version history to investigate failures and restore an earlier working version.
- Do not claim that a skill is production-ready merely because its source file exists.

## 5. Skill Specification and Lifecycle

### 5.1 Explicit skill specification

Each skill creation or adaptation request must produce a validated specification containing the fields appropriate to the existing repository schema, including:

- Stable skill ID.
- Name and concise purpose.
- Version.
- Skill category/domain and capability tags.
- Inputs, types, constraints, and required fields.
- Outputs and their expected format.
- Execution interface or entry point.
- Dependencies and runtime requirements.
- Validation and behavioral test requirements.
- Security risk classification.
- Origin and provenance.
- Creation/adaptation rationale.
- Source and test artifact references.
- Lifecycle status and approval evidence.

Inspect the existing schemas and consumers before deciding field names or adding required fields. Do not break existing skill manifests.

Reject malformed specifications before generation or promotion. Missing information that materially affects safety or behavior must produce an explicit clarification request or a safe, documented rejection.

### 5.2 Existing-skill discovery and decision

Integrate the Skill Factory with the existing Capability Finder, Capability Registry, and Skill Registry.

Use this order:

1. Reuse an active, compatible skill.
2. Adapt an active skill when the capability is close enough and adaptation is justified.
3. Create a new skill when the available reusable capabilities are insufficient.

The Skill Factory must not independently contradict a verified reuse decision without a concrete, recorded reason.

For create/adapt decisions, preserve the original requirement and record why the selected approach is appropriate.

### 5.3 Generation and adaptation

Inspect the configured model/provider interface and existing code-generation conventions.

Use the existing supported provider infrastructure to generate or adapt skill source code where appropriate. Avoid hardcoding provider keys, model credentials, local secrets, or model-specific behavior into the Skill Factory.

Generated code must be an actual implementation of the declared skill interface. It must not be an empty placeholder, a fake success response, or a hardcoded answer that ignores its inputs.

If the model/provider service is unavailable, fail clearly and safely. Do not report a draft as successfully generated when generation did not occur.

Generated output must satisfy the skill specification, runtime contract, and validation requirements before it can proceed.

## 6. Static Security Validation and Safe Testing

### 6.1 Static validation

Reuse and strengthen existing AST-based validation and security checks where available.

Inspect the complete proposed skill, relevant imports, entry points, dependencies, and metadata. Detect and appropriately reject or quarantine risky behavior, including:

- Credential, token, password, or secret exfiltration.
- Unauthorized filesystem access.
- Unexpected process execution or shell commands.
- Unapproved network access.
- Unsafe dynamic code execution or import behavior.
- Destructive file operations.
- Attempts to access unrelated project or user data.
- Attempts to alter the frozen pipeline algorithms.
- Attempts to bypass approval gates or write directly into active registries.
- Unbounded recursion, uncontrolled resource use, or other unsafe execution patterns.

Do not rely only on suspicious-string checks when the risk requires structural analysis. Preserve source references and actionable diagnostics for rejected findings.

False positives should be handled through an explicit review mechanism, not by automatically bypassing security validation.

### 6.2 Safe behavioral testing

Do not execute newly generated or untrusted code directly inside the unrestricted application process.

Inspect the existing execution environment and implement an appropriate isolation strategy for the supported platform. On Windows, use the project's available sandboxing or operating-system isolation mechanisms, if present. If no adequate isolation exists, do not pretend that a normal subprocess or temporary directory constitutes a complete security sandbox.

At minimum, the implementation must:

- Use a controlled temporary workspace.
- Apply bounded execution timeouts.
- Enforce appropriate resource and filesystem restrictions supported by the environment.
- Prevent generated tests from modifying production registries, active knowledge, secrets, or frozen files.
- Capture standard output, standard error, exit status, and structured test results.
- Terminate timed-out test workers safely.
- Clean up temporary artifacts without deleting unrelated user data.
- Clearly distinguish security validation from behavioral correctness testing.

If the available platform cannot provide the required isolation for a specific skill, classify that skill as blocked from execution/promotion, report the missing isolation capability, and offer a safe non-executing validation path. Do not claim that an unisolated test is secure.

### 6.3 Test quality

Test the declared skill inputs and outputs, expected successful behavior, invalid inputs, boundary conditions, failure behavior, and relevant security conditions.

Do not accept a skill solely because its source parses or because it exits with code zero. Validate that the implementation behaves according to its specification.

## 7. Approval and Promotion Workflow

Integrate with the existing approval services, including the established trusted identity and role verification path where applicable.

Never treat a caller-supplied role string, proposal field, or `authorized_by` text alone as proof of authorization.

Use appropriate approvals according to the project's existing risk policy.

A suggested lifecycle, subject to compatibility with existing schemas, is:

`DRAFT → VALIDATING → TESTING → AWAITING_APPROVAL → APPROVED → PROMOTING → ACTIVE`

Alternative terminal states may include:

`REJECTED`, `QUARANTINED`, `FAILED_VALIDATION`, `FAILED_TESTS`, `PROMOTION_FAILED`, and `ROLLED_BACK`.

Implement these states coherently without creating duplicate status systems or silently changing existing persisted values.

Rules:

1. A security failure must prevent promotion.
2. A required test failure must prevent promotion.
3. An outstanding approval must prevent promotion.
4. An unauthorized caller must not approve or promote a skill.
5. A failed or interrupted promotion must not expose a partially written active skill.
6. Drafts and rejected skills must not appear as usable production capabilities.
7. A successful promotion must record its version, source, validation/test evidence, approval identity, timestamp, and provenance.
8. Existing approval policy must not be weakened merely to simplify the workflow.

**Approval boundary:** If the established architecture requires a manual approval at a stage, preserve it. Do not replace an explicit manual approval with an automatic pass. Where automated promotion is already permitted by approved policy, use the appropriate existing verification mechanism.

## 8. Versioning, Atomic Promotion, and Rollback

Implement a reliable publication workflow using the project's existing storage conventions.

Before promotion:

- Validate the skill package and metadata.
- Confirm required security and behavioral checks passed.
- Confirm required authorization is valid.
- Check version and publication conflicts.
- Confirm that the destination is within the intended skill library.

During promotion:

- Write to a temporary location on the same filesystem where atomic replacement is required.
- Flush and synchronize data where appropriate.
- Use safe atomic replacement for the supported filesystem.
- Ensure the registry never references an incomplete artifact.
- Preserve recoverable prior metadata and versions.
- Avoid publishing duplicate or conflicting skill IDs and versions.
- Protect transactions against concurrent publication or rollback where concurrent operations are supported.

After promotion:

- Verify the published artifact exists and matches the expected content hash.
- Verify the active registry points to the correct version.
- Verify the Capability Registry can discover the newly active skill.
- Record the final publication result and evidence.

Rollback must restore a known valid prior version and reconcile the related registry state. It must not simply remove arbitrary files or leave the active registry pointing at a missing version.

Treat package files, manifests, registry entries, and archive state as a coherent publication transaction. If full atomicity across those resources is not possible, implement explicit recovery/reconciliation logic and document the exact guarantees.

Do not delete previous valid skill versions merely to simplify storage.
